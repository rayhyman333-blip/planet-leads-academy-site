This lesson teaches you to test like a professional: on real devices, across the conditions users actually face, with a system for finding and fixing bugs. By the end you will build a device test plan, reproduce the most common mobile issues, and run beta testing with real users. Simulators and emulators on your computer are useful for development, but they lie about performance, touch feel, battery, and network — real devices are where truth lives.

Build a test matrix before you test. Rows are devices: cover both platforms, old and new operating-system versions, small and large screens, and at least one low-end device with limited memory — budget phones expose performance sins that flagship phones hide. Columns are conditions: fresh install, upgrade from the previous version, low storage, low battery, dark mode, large text sizes, different languages if you support them, and poor or absent network. You do not need to own them all: borrow, use a device lab service, or recruit testers with diverse phones (Lesson 8's beta). The matrix turns "test the app" from a vague wish into checkable boxes.

Walk the matrix systematically. Fresh install: does first-run onboarding work, are permissions asked in context, does the app survive denial? Core flows: complete every primary task end to end on a real device with your thumb, on cellular data, while walking — real usage, not desk usage. Interruptions: take a phone call mid-form, switch apps mid-upload, lock the screen mid-task, then return — state must survive all of it. Upgrades: install the old version, create data, install the new version over it — data must migrate cleanly. Stress: fill storage nearly full, enable the slowest network mode, rotate the screen mid-flow, enable the largest text size — layout must not break.

Learn the classic mobile bugs so you recognize them. Crash on launch: usually bad saved data from a previous version or a failed migration — clear test: fresh install works, upgrade crashes. Layout overflow: content wider than small screens or text sizes that break fixed layouts — the large-text test catches these. Frozen interface: network requests blocking the main thread — the app must never wait synchronously on the network (Lesson 6). Battery drain: background work running wild — background tasks must be brief, batched, and deferrable. Lost data: writes that lived only in memory when the app was killed — save important input immediately (Lesson 5). Notification failures: permissions denied or tokens expired — test the denied-permission path, not just the happy path.

Fix bugs with a system, not hope. One, reproduce reliably: find the exact steps that trigger it every time — a bug you can trigger on demand is a bug you can fix and verify. Two, isolate: disable suspects one at a time (network? a specific screen? a specific device?) until the trigger narrows. Three, fix one thing and re-test the exact reproduction steps — plus the neighboring flows, because fixes break neighbors. Four, write the regression check into your test matrix so the bug can never silently return. Keep a simple bug log: what, on which device and OS, steps to reproduce, suspected cause, fix, verified. This log becomes your release notes and your institutional memory.

Beta testing puts the app in strangers' hands before launch. Recruit 10–50 testers who resemble real users (not just tech-savvy friends), distribute through the platforms' official beta channels, and give them a mission: "use it as you normally would for a week, and report anything confusing, slow, or broken." Ask specific questions afterward: what was confusing in the first minute? Where did you get stuck? What did you expect to happen that didn't? Watch one tester use it without helping — five minutes of silent observation teaches more than fifty survey responses. Fix crashes first, confusion second, polish last.

Two mistakes to avoid. First, testing only on your own phone: your flagship device on fast wifi is the least representative environment imaginable. Second, treating beta feedback as votes: ten testers requesting ten different features is noise — but three testers independently confused by the same screen is signal. Fix confusion; defer feature requests until after launch.

Practice: In your journal, build the test matrix for your app idea: at least six device/OS combinations and eight conditions from this lesson. Then take any app on your phone and run a five-minute "hostile test": airplane mode on, largest text size, low-power mode — note everything that breaks or degrades gracefully. Write up the findings as if reporting to a developer: what you did, what you expected, what happened. Finally, draft your beta recruitment message: who you need, what you will ask them to do, and your three follow-up questions.
