This lesson teaches you how apps talk to the internet: what web services and APIs are, how apps request data, and how to handle the loading, failure, and offline realities of networks. By the end you will describe the request-response cycle in plain language, design good loading and error states, and plan caching and offline behavior. Almost every useful app is a conversation between the device and distant computers — this lesson is that conversation's grammar.

A web service is a computer on the internet that does something for your app: stores data, processes requests, sends messages. An API (Application Programming Interface) is the agreed-upon language for asking: the set of addresses (endpoints) your app can call and the format of what comes back. In plain terms: your app sends a structured request ("GET the current weather for this city"), the service processes it, and returns structured data ("72°F, sunny"). Your app then displays it. The app never touches the service's internals; it only speaks the API's public language. Many services publish public APIs (weather, maps, transit, payments), and companies build private APIs connecting their own apps to their own servers.

The request-response cycle has four stages, and each can fail. One, the app builds the request — wrong format here means the service rejects it immediately. Two, the network carries it — slow, absent, or interrupted connections stall or kill it here. Three, the service processes it — bugs or overload on their end return errors. Four, the app receives and displays the result — unexpected data shapes crash careless apps here. Robust apps distrust every stage: they set timeouts (give up gracefully after N seconds rather than spinning forever), retry sensibly (once or twice for network blips, never in a tight infinite loop), and validate responses before using them.

Loading states are where apps earn or lose trust. Any network request slower than a blink needs visible feedback: a spinner or skeleton screen for short waits, a progress indicator with cancel for long ones. Never freeze the interface — the app must stay responsive while waiting, and the user must always be able to back out. Empty and error states deserve the same design care as success: "Couldn't load your messages. Check your connection and try again. [Retry]" with the retry button right there beats a blank screen or a technical error code. Log the technical details for yourself; show the human words to the user.

Caching — keeping copies of fetched data on the device (Lesson 5) — makes apps feel instant and work offline. Cache aggressively for content that changes slowly (user profiles, reference data, yesterday's articles) with clear freshness stamps; fetch fresh for content that changes fast (prices, availability, messages) while still showing the cached copy first. A graceful pattern: show cached data immediately, refresh silently in the background, update the display when new data arrives, and say "updated just now". The user perceives speed; the app maintains accuracy.

Authentication — proving who the user is — usually means the app sends a username and password once, receives a token (a long secret string meaning "this device may act as this user"), and stores that token securely (Lesson 5's secure storage). Tokens expire; plan the refresh flow so users are not randomly logged out mid-task. Never put secrets in the app's code itself — anything shipped in the app can be extracted. And design for the logged-out state as a first-class experience, not an error: what can a signed-out user still see and do?

Two mistakes to avoid. First, the happy-path app: designed only for fast wifi and correct responses, it collapses the first time a user opens it in a parking garage. Test every screen on airplane mode before launch — Lesson 7 makes this systematic. Second, chatty networking: fetching data in tiny repeated requests drains batteries and data plans. Batch requests, cache smartly, and fetch in the background only what the user will plausibly need.

Practice: In your journal, list every network request your app idea needs (login, fetching items, saving changes, images). For each, write: what triggers it, what the loading state shows, what the error state says (exact words), and what the offline behavior is. Then sketch your app's "airplane mode" experience screen by screen — what works, what waits, what explains itself. If any screen has no graceful offline behavior, redesign it now, while it is still paper.
