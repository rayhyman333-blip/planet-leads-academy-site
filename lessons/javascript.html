Go from your first script to interactive web apps with the DOM, events, and modern JavaScript.

Lesson 1: Setup and Your First Script

This lesson gets you running JavaScript with zero installation, using the browser you already have. By the end you will know how to open the developer console and run code instantly, how to put a script inside a web page with script tags, and how to store values in variables with let and const. You will also write your first real code: console.log() for showing output. Everything in this lesson is about getting comfortable with the tools, so run every example yourself as you read.

JavaScript was born in the browser, which means your setup is already done. Open your browser, press F12 (or right-click any page and choose Inspect), and click the Console tab. You will see a prompt where you can type JavaScript and press Enter to run it immediately. Try typing console.log("Hello, world!") and pressing Enter — the message appears in the console. Try 2 + 3 and you will see 5. The console is your scratchpad for the whole course: whenever you wonder what a piece of code does, test it here in seconds instead of guessing. Nothing you type in the console changes the website permanently — reloading the page wipes it clean, so experiment freely.

The console is great for experiments, but real JavaScript lives inside web pages. Create a file called hello.html in a plain text editor, type the following, save it, and open it in your browser by double-clicking the file:

<!DOCTYPE html> <html> <body> <h1>My first script</h1> <script> console.log("Hello from the page!"); console.log("2 + 3 is", 2 + 3); </script> </body> </html>

The script tags mark where JavaScript lives inside the HTML. When the browser loads the page, it runs the code between them top to bottom. Open the console (F12) with this page open and you will see both messages — the page itself shows the heading, while the console shows your script's output. That split is normal: console.log() is a developer tool for seeing what your code is doing, and you will use it in every lesson to check your work.

Variables store values under names so you can reuse them. JavaScript has two main ways to declare them:

let name = "Maya"; let age = 30; const birthYear = 1995;

Use let for values that will change (age = 31 later is fine) and const for values that should never be reassigned — trying birthYear = 2000 after declaring it const is an error. The const habit protects you: most values in a program never need to change, and const makes accidental changes impossible. Names follow the same rules as in most languages: letters, digits, underscores, and dollar signs, but no starting with a digit and no spaces. JavaScript convention writes multi-word names in camelCase — firstName, totalPrice — so adopt that style from day one. Like Python, JavaScript is case-sensitive: Age and age are different variables.

One more console trick that will save you hours: when something goes wrong, the console shows the error in red with a line number. Clicking the line number jumps to the failing code. Get into the habit of keeping the console open whenever you test a page — silent pages hide their errors, but the console always tells the truth.

Two beginner mistakes cause most Lesson 1 frustration. First, quoting: console.log("hi') fails because the opening double quote must close with a double quote. Pick one style per string and match it. Second, forgetting to save the file before reloading the browser, then wondering why nothing changed — the browser only knows about the saved version, so save, then reload, then check the console. If your script "does nothing," those two checks solve it most of the time.

Practice: Create greeting.html with a script that declares a const called name holding your name, a let called hobby holding your favorite hobby, and uses console.log() to print two lines, for example "Hi, I'm ..." and "I enjoy ...". Open the page, open the console, and confirm both lines appear. Then, in the console itself (not the file), experiment: type let testScore = 95; then testScore + 5; then const city = "Austin"; then try city = "Denver"; and read the error message. Notice how the console tells you assignment to a constant is not allowed — reading errors calmly is a skill you will use in every lesson.

Lesson 2: Types, Operators, and Conditionals

This lesson teaches you the building blocks every JavaScript program is made of: the core data types, the operators that combine them, and if/else statements for making decisions. By the end you will know the difference between strings, numbers, booleans, null, and undefined; you will use strict equality to avoid JavaScript's most famous trap; and you will write programs that choose different paths based on conditions. These ideas appear in every lesson after this one, so run each example in your console before moving on.

JavaScript has a small set of core types you will use constantly. A string is text in quotes: "hello", 'JavaScript', "42". A number covers both integers and decimals: 7, 3.5, -20 — JavaScript does not separate the two the way some languages do. A boolean is true or false, written lowercase. Then come the two "empty" values: null means "intentionally no value" (you set it on purpose), while undefined means "no value has been assigned yet" (JavaScript's default for untouched variables). The typeof operator tells you what you are holding: typeof "hello" gives "string", typeof 42 gives "number", typeof true gives "boolean". Types matter because JavaScript treats "42" (text) and 42 (a number) very differently, as you will see with operators next.

Arithmetic operators work like a calculator: + - * /, plus % for remainder (7 % 2 gives 1) and ** for powers (2 ** 3 gives 8). The + operator on strings joins them, called concatenation: "Good " + "morning" gives "Good morning". Here is JavaScript's famous trap: "5" + 3 gives "53", not 8, because + with a string converts the other side to text. To convert deliberately, use Number("5") to get 5 and String(42) to get "42". Now the equality trap: JavaScript has two kinds. Loose equality == converts types before comparing, so "5" == 5 is true — usually not what you want. Strict equality === compares without converting, so "5" === 5 is false. The rule professionals follow: always use === and !==, never == and !=, and an entire category of mysterious bugs disappears.

Comparison operators ask questions and answer with booleans: === checks equality, !== checks inequality, and < > <= >= compare size. Logical operators combine them: && means "and" (true only if both sides are true), || means "or" (true if either side is true), and ! flips a value. So age >= 18 && hasTicket gives true only when both hold. An if statement runs a block only when its condition is true:

const age = Number(prompt("Enter your age:")); if (age >= 18) { console.log("You are an adult."); } else { console.log("You are under 18."); }

Note the parentheses around the condition and the curly braces marking each block — every indented statement between the braces belongs to that branch. For more paths, add else if branches: they are checked top to bottom and the first true one runs. The prompt() function here shows a pop-up asking for input and returns whatever was typed as a string, which is why we wrap it in Number() — the same string-input catch you would expect from any language.

Two mistakes dominate this lesson. First, using == instead of ===: "0" == false is true under loose equality, a genuinely baffling result that strict equality avoids entirely. If a comparison behaves impossibly, check which equality operator you used. Second, the assignment-in-condition slip: if (x = 5) assigns 5 to x and is always truthy, while if (x === 5) actually compares. Read = as "gets" and === as "is exactly" and your brain will flag the mix-up. A related gotcha: prompt() always returns a string, so comparing its result with a number using === fails unless you convert first with Number().

Practice: In your console, evaluate each of these and make sure you can explain the result before checking: "10" + 5, 10 + 5, Number("10") + 5, "5" === 5, "5" == 5, 0 === false, !true, and (7 > 3) && (2 < 1). Then create grade.html with a script that uses prompt() to ask for a test score, converts it with Number(), and logs "Grade: A" for 90+, "Grade: B" for 80+, "Grade: C" for 70+, and "Grade: below C" otherwise, using if/else if/else. Test it with 95, 82, and 64, and also test typing a non-number to see what happens — note the result, because handling that gracefully is a skill you will build on later.

Lesson 3: Functions, Arrays, and Objects

This lesson teaches you to organize code into reusable functions and to manage collections of data with arrays and objects. By the end you will define functions with parameters and return values, create and manipulate arrays, model real things with objects, and loop over collections. Functions plus collections are the engine room of JavaScript: nearly every interactive page you build from Lesson 4 onward runs on these three ideas.

A function is a named, reusable block of code. You have already used built-in ones like console.log() and Number(); defining your own looks like this:

function greet(name) { return "Hello, " + name + "!"; }

const message = greet("Ava"); console.log(message); // Hello, Ava! console.log(greet("Ben")); // Hello, Ben!

The function line names it (greet) and lists its parameters — the inputs it expects. Calling greet("Ava") passes "Ava" in as the argument, so name becomes "Ava" for that call. The return statement sends a value back to the caller: message receives "Hello, Ava!". The rule of thumb: console.log() is for showing humans, return is for giving values back to your program so it can keep working with them. A function without return still runs, but calling it gives back undefined. Parameters can have defaults — function greet(name, greeting = "Hello") — making them optional, and a function can call other functions, which is how small pieces compose into bigger behavior.

An array is an ordered list written with square brackets: const scores = [85, 92, 78]. Items are numbered from 0, so scores[0] is 85. Useful tools: scores.length gives the count, scores.push(90) adds to the end, scores.pop() removes and returns the last item. Loop over arrays with a classic for loop or the friendlier for...of: for (const score of scores) { console.log(score); } visits each item in order. Arrays hold the lists of things your apps display — tasks, products, messages — so get fluent with them now.

An object groups related values under named keys, written with curly braces: const person = { name: "Ava", age: 30, city: "Austin" }. Read values with dot notation — person.name — or bracket notation — person["name"] — which is handy when the key is stored in a variable. Add or change with person.email = "ava@example.com", and nest freely: objects inside arrays, arrays inside objects. A task in our capstone app will be an object like { text: "Buy milk", done: false }, and the whole list will be an array of those objects — a pattern you will see in real applications everywhere. Loop over an object's keys with for (const key in person) when you need to inspect every property.

Scope determines where a variable can be seen. Variables declared with let or const inside a function exist only while it runs; variables declared at the top level of your script are visible everywhere below. A classic mistake is declaring a variable inside an if block with let and trying to use it after the block ends — it does not exist there. The fix is to declare it in the wider scope first, then assign inside the block. Keeping data flowing through parameters and return values, rather than shared globals, makes functions predictable and testable.

Two mistakes are classic here. First, the off-by-one error: the last item of a 4-item array is scores[3], not scores[4], and scores[4] gives undefined instead of crashing — JavaScript fails silently where other languages shout, so always double-check indexes. Second, treating undefined as a value: reading a misspelled property like person.nam gives undefined, and then person.nam.toUpperCase() crashes.

When you see "cannot read properties of undefined", look one step earlier — the property name or the object itself is not what you think.

Practice: Create contacts.html with a script that stores contacts as an array of objects, starting with two you invent ({ name, phone, email } keys). Write three functions: addContact(list, name, phone, email) that pushes a new object and returns the list; findContact(list, name) that loops and returns the matching object or null; and showContacts(list) that logs each contact on one readable line. At the bottom, call them in sequence: show the starting list, add a third contact, show the list again, and search for a name that does not exist — confirm your function returns null without crashing. Test everything in the console and read each output line to verify it says what you expect.

Lesson 4: The DOM — Selecting and Changing Page Elements

This lesson teaches you the Document Object Model: JavaScript's live map of the web page, and the tool you use to change what visitors see. By the end you will select elements by id and with CSS-style selectors, read and change their text, adjust their styles, and create brand-new elements from code. The DOM is what turns JavaScript from a console curiosity into the language of interactive pages — every dynamic website you have ever used runs on these operations.

The DOM is the browser's tree-shaped representation of your HTML: every tag becomes a node you can reach from JavaScript. To work with an element, first give it an id in the HTML, then grab it:

<h1 id="title">Welcome</h1> <p id="message">Loading...</p>

<script> const titleEl = document.getElementById("title"); const msgEl = document.querySelector("#message"); console.log(titleEl.textContent); // Welcome </script>

document.getElementById grabs one element by its id, while document.querySelector takes any CSS selector — "#message" for an id, ".warning" for a class, "button" for a tag — and returns the first match (querySelectorAll returns all matches). Once you hold an element, textContent reads or sets its text: msgEl.textContent = "Hello, Ava!"; rewrites the paragraph instantly. Prefer textContent over innerHTML for plain text: innerHTML interprets the string as HTML, which is powerful but dangerous with user-supplied text, while textContent treats everything as literal characters and is always safe. innerHTML has legitimate uses — inserting your own static markup, like building a card from a template literal — but treat any string containing user input as textContent-only territory.

Changing styles is just as direct — every CSS property is available in camelCase on the element's style object:

titleEl.style.color = "darkblue"; titleEl.style.fontSize = "40px"; msgEl.classList.add("highlight");

Note backgroundColor instead of background-color: CSS's hyphens become camelCase in JavaScript. The classList approach is often cleaner than inline styles: define a .highlight class in a <style> block, then add or remove it with classList.add() and classList.remove(), or flip it with classList.toggle(). This keeps your styling in CSS where it belongs and your JavaScript focused on behavior — a separation professionals maintain strictly.

You can also build elements from scratch, which is how apps render lists of data:

const listEl = document.getElementById("tasks"); const item = document.createElement("li"); item.textContent = "Buy milk"; item.classList.add("task"); listEl.appendChild(item);

document.createElement("li") builds a new list item, you configure it like any selected element, and appendChild attaches it inside the list. This create-configure-attach pattern is the heart of dynamic pages: your data lives in arrays and objects (Lesson 3), and a render function turns that data into elements. You can set several properties before attaching — text, class, even nested children — and nothing appears on the page until appendChild runs, which lets you build complex structures offscreen and insert them in one step. The capstone app in Lesson 8 is essentially this pattern plus events.

Two mistakes dominate DOM work. First, running your script before the elements exist: if the script tag sits in the head and tries getElementById("title"), it gets null because the body has not loaded yet. The

simple fix is placing your script tag at the end of the body, right before </body>, so all elements exist when it runs. Second, calling methods on null: when a selector finds nothing, you get null, and null.textContent crashes with "cannot read properties of null". When that error appears, your selector is wrong or the element is missing — console.log the variable first and confirm it holds an element before touching it.

Practice: Create profile.html with an h1 (id="name"), a paragraph (id="bio"), and an empty ul (id="hobbies"). Write a script at the end of the body that: sets the h1's text to your name, sets the bio paragraph to two sentences about you, changes the h1's color, and creates three li elements from an array of your hobbies ["reading", "cycling", "cooking"] using a for...of loop with createElement and appendChild. Open the page and confirm everything renders. Then, in the console, try document.querySelector("#does-not-exist") and observe the null — then try setting .textContent on it to see the exact error, so you recognize it instantly in future lessons.

Lesson 5: Events — Clicks, Input, and Form Submission

This lesson teaches your pages to respond to users through events: the browser's way of announcing that something happened. By the end you will listen for clicks, react to typing as it happens, handle form submissions without reloading the page, and read information from the event object. Events are what make pages feel alive — without them, Lesson 4's DOM skills can only produce static pages that never react.

An event listener waits for something to happen on an element, then runs your function:

<button id="likeBtn">Like (0)</button> <script> const btn = document.getElementById("likeBtn"); let likes = 0; btn.addEventListener("click", function () { likes = likes + 1; btn.textContent = "Like (" + likes + ")"; }); </script>

addEventListener takes the event name ("click") and a callback function that runs each time the event fires. The variable likes persists between clicks because it lives outside the callback — each click reads the current value, adds one, and rewrites the button's text. This pattern (state in a variable, event updates state, DOM re-renders) underlies every counter, toggle, and like button on the web. You can attach multiple listeners to the same element, and one callback can update several elements at once.

The input event fires on every keystroke inside a text field, which enables live feedback like character counters:

<label>Your message: <input id="msg" type="text"></label> <p id="count">0 / 140</p> <script> const field = document.getElementById("msg"); const count = document.getElementById("count"); field.addEventListener("input", function () { count.textContent = field.value.length + " / 140"; }); </script>

The .value property holds what the user typed. Reading it inside the input handler means the count updates with every keystroke — try it and watch. This immediate loop (user acts, event fires, page updates) is the signature feel of modern web apps, and it is built entirely from pieces you already know: selection, properties, and text updates.

Forms need one special technique. A form's submit event reloads the page by default, wiping your JavaScript state — to handle submission in code, you must cancel that default behavior:

<form id="taskForm"> <label>New task: <input id="taskInput" type="text"></label> <button type="submit">Add</button> </form> <ul id="taskList"></ul> <script> const form = document.getElementById("taskForm"); const input = document.getElementById("taskInput"); const list = document.getElementById("taskList"); form.addEventListener("submit", function (event) { event.preventDefault(); const text = input.value.trim(); if (text === "") { return; } const item = document.createElement("li"); item.textContent = text; list.appendChild(item); input.value = ""; }); </script>

The event object, received as the callback's parameter, describes what happened; event.preventDefault() stops the browser's default reload. We trim whitespace and ignore empty submissions, create the list item with Lesson 4's pattern, and clear the field for the next entry. This is a miniature version of the capstone app — the only things missing are persistence and delete buttons, both coming in Lesson 8.

Two mistakes are classic here. First, forgetting preventDefault on submit: the page reloads, your added items vanish, and it looks like the code "didn't work" — it did work, then the reload erased it. If form handling ever seems to do nothing, check for preventDefault first. Second, attaching a listener to null because the id in getElementById does not match the HTML — ids are case-sensitive, so "taskForm" and "taskform" are different. When a button "does nothing," console.log the element right after selecting it; null means the selection failed, not the listener.

Practice: Create counter.html with three buttons ("Decrease", "Reset", "Increase") and a paragraph showing a number starting at 0. One listener per button should update the number and re-render the paragraph — decrease must not go below 0 (use an if). Then create signup.html with a form containing a name field and an email field plus a paragraph for messages. On submit, prevent the default reload; if either field is empty, show "Please fill in both fields." in the message paragraph; otherwise show "Thanks, <name>! We will write to <email>." and clear the form. Test every path, including submitting with empty fields and watching the page stay put.

Lesson 6: Modern JavaScript — Arrows, Templates, and Destructuring

This lesson teaches the modern JavaScript features that make code shorter and clearer: arrow functions, template literals, and destructuring, plus a few companion tools. By the end you will rewrite callbacks as one-line arrows, build strings with embedded expressions instead of messy concatenation, and pull values out of objects and arrays in a single statement. You will see these features in nearly every real-world codebase, so fluency here is what makes other people's code readable to you.

Arrow functions are a compact way to write functions, and they shine as event callbacks:

// traditional btn.addEventListener("click", function () { console.log("clicked"); });

// arrow btn.addEventListener("click", () => { console.log("clicked"); });

The () => syntax replaces function (). With a single parameter the parentheses are optional — x => x * 2 — and with a single expression the braces and return are implied: const double = x => x * 2; means "take x, return x * 2". Multi-line arrows keep braces and an explicit return. One caution: arrows handle the special this value differently from traditional functions, treating it as the surrounding context instead of the element that fired the event. For the event handlers in this course you do not need this at all — but if you ever copy code that uses this inside a handler, know that switching it to an arrow can change its meaning, so leave traditional functions in place there.

Template literals replace fiddly string concatenation. They use backticks instead of quotes, and ${} embeds any expression:

const name = "Ava"; const unread = 3; const msg = `Hello, ${name}! You have ${unread} unread messages.`; console.log(msg); // Hello, Ava! You have 3 unread messages.

Compare that with "Hello, " + name + "! You have " + unread + " unread messages." — the template version reads like the final sentence. The ${} can hold any expression: ${unread + 1}, ${user.name.toUpperCase()}. Backticks also allow multi-line strings, so HTML snippets stay readable: const card = `<div class="card"><h2>${title}</h2><p>${body}</p></div>`;. From now on, prefer templates whenever a string contains variables.

Destructuring unpacks values in one move. From objects:

const user = { name: "Ava", age: 30, city: "Austin" }; const { name, age } = user; console.log(name); // Ava

The variable names must match the keys. From arrays, position matters instead: const [first, second] = scores; grabs the first two items, and you can skip with commas: const [, runnerUp] = scores;. Function parameters destructure too — function showUser({ name, city }) — which makes it obvious which properties a function needs. Combined with the spread operator (...), you get effortless copies and merges: const updated = { ...user, age: 31 }; copies user with a new age, and const all = [...listA, ...listB]; joins arrays. Spread copies are shallow but perfectly adequate for the data shapes in this course.

Two mistakes catch beginners here. First, using regular quotes with ${}: "Hello, ${name}" prints the literal characters ${name} — interpolation only works inside backticks, so when variables refuse to fill

in, check the quote character. Second, destructuring a missing property gives undefined silently: const { email } = user where user has no email key leaves email undefined, and using it later crashes far from the real cause. When a destructured value is unexpectedly undefined, verify the key name against the object — spelling and case must match exactly.

Practice: Rewrite the like-button code from Lesson 5 using an arrow function and a template literal for the button text (`Like (${likes})`). Then, in the console, practice destructuring: create const order = { id: 101, item: "headphones", price: 59.99, qty: 2 }; and use destructuring plus a template literal to log "Order 101: 2 x headphones = $119.98" with the total computed as ${price * qty} inside the string. Next, merge two arrays with spread and log the result. Finally, convert one of your Lesson 3 functions to an arrow function assigned to a const, call it, and confirm identical behavior — this cements when arrows are a safe swap.

Lesson 7: Fetching Data — JSON and the Fetch API

This lesson teaches your pages to load data from the web: the skill behind every feed, search result, and live dashboard you have ever used. By the end you will understand JSON as a data format, request it with the Fetch API, handle the asynchronous wait for a response, and render what comes back into your page. Fetching turns your apps from closed boxes into connected ones — the capstone's tasks come from the user, but the same techniques display data from anywhere.

JSON (JavaScript Object Notation) is the standard format for data on the web, and it looks like JavaScript objects and arrays written as text:

{ "id": 7, "title": "Write report", "done": false, "tags": ["work", "urgent"] }

Keys are quoted strings, values can be strings, numbers, booleans, null, arrays, or nested objects. JavaScript converts between JSON text and real values with two functions: JSON.parse(text) turns a JSON string into an object you can use, and JSON.stringify(value) turns an object back into text (useful for storage, as Lesson 8 will show). When a server sends data, it arrives as JSON text; your first job is always to parse it into something workable.

The Fetch API requests data from a web address. Because the response takes time to arrive, fetch does not return the data directly — it returns a promise, a stand-in object representing "the result, when it comes". The modern way to wait for it is async/await:

async function loadTasks() { try { const response = await fetch("https://example.com/api/tasks"); if (!response.ok) { throw new Error("Server responded with " + response.status); } const tasks = await response.json(); console.log(tasks); } catch (error) { console.log("Could not load tasks:", error.message); } } loadTasks();

Walk through it: await fetch(...) pauses the function until the response headers arrive; response.ok is false for errors like 404, so we check it and throw our own error rather than parsing garbage; await response.json() pauses again while the body downloads and parses; any failure at any step lands in catch. The try/catch from Lesson 6's error philosophy applies directly — network requests fail for ordinary reasons (no connection, wrong address, server down), so every fetch needs a catch. Note the example address is illustrative: replace it with a real JSON endpoint when you experiment, such as a public demo API that returns sample data.

Rendering fetched data uses your DOM skills in a loop. Suppose the endpoint returns an array of task objects with title and done properties:

async function renderTasks() { const listEl = document.getElementById("tasks"); try { const response = await fetch("https://example.com/api/tasks"); if (!response.ok) { throw new Error("Bad response: " + response.status); } const tasks = await response.json(); listEl.textContent = ""; for (const task of tasks) { const item = document.createElement("li"); item.textContent = task.done ? "Done: " + task.title : task.title; listEl.appendChild(item); } } catch (error) { listEl.textContent = "Could not load tasks. Check your connection."; } }

This is the full professional pattern: clear old content, fetch, validate, parse, loop and render — with a friendly message if anything fails. The ternary (condition ? a : b) is a compact if/else for choosing between two values, handy inside rendering code. Notice the user never sees a crash or a blank page: failure produces an honest message, which is how real apps behave.

Three mistakes are classic here. First, forgetting await: without it, response is a promise, not a response, and response.ok is undefined — if your fetch "returns nothing useful," check for missing await. Second, skipping the response.ok check and calling response.json() on an error page, which throws a confusing parse error instead of telling you the address was wrong. Third, trying to use fetched data outside the async function before it arrives — code after loadTasks() runs immediately, not after the data lands. Keep all data-dependent work inside the async function (or in functions it calls) until this timing feels natural.

Practice: Create fetch-demo.html with an empty ul (id="posts") and a paragraph (id="status"). Write an async function that fetches from a real public JSON demo endpoint of your choice (search for "public JSON demo API" — several free ones return sample posts with title fields), checks response.ok, parses the JSON, and renders the first five titles as list items. Show "Loading..." in the status paragraph before the fetch and clear it on success, or show an error message on failure. Test twice: once with the correct address, once with a deliberately wrong address, and confirm the failure case shows your friendly message instead of a console-only error.

Lesson 8: Capstone — Interactive To-Do App and Next Steps

This final lesson puts the whole course together in one capstone project: a complete interactive to-do app that adds tasks, marks them complete, deletes them, and saves everything in the browser so tasks survive reloads. By the end you will have combined DOM selection, events, modern JavaScript, and persistent storage in one page, and tested it like a user would. It closes with a map of where to go next.

Start every project by listing features in plain language before writing code. Our app needs five: 1) add a task from a form; 2) display all tasks as a list; 3) toggle a task complete/incomplete; 4) delete a task; 5) save tasks in the browser and reload them at startup. Each maps to a lesson: forms and events (Lesson 5), DOM creation (Lesson 4), arrays of objects (Lesson 3), template literals and arrows (Lesson 6), JSON for storage (Lesson 7). Asking which lesson taught a piece is how you break big projects down.

The data layer is an array of task objects plus two persistence functions. localStorage is a small key-value store built into every browser that survives page reloads — but it only stores strings, so we convert with JSON:

const STORAGE_KEY = "my-tasks-v1";

function loadTasks() { try { const saved = localStorage.getItem(STORAGE_KEY); return saved ? JSON.parse(saved) : []; } catch (error) { return []; } }

function saveTasks(tasks) { localStorage.setItem(STORAGE_KEY, JSON.stringify(tasks)); }

Each task is { text: "Buy milk", done: false }. loadTasks handles the first visit (nothing saved returns []) and even corrupted data (parse failure returns [] instead of crashing). Test in the console by saving a sample array and loading it back.

Rendering turns the data into elements, and every user action follows the same cycle: update the array, save it, re-render:

let tasks = loadTasks(); const listEl = document.getElementById("taskList");

function render() { listEl.textContent = ""; tasks.forEach((task, index) => { const item = document.createElement("li"); const label = document.createElement("span"); label.textContent = task.text; if (task.done) { label.style.textDecoration = "line-through"; } const toggleBtn = document.createElement("button"); toggleBtn.textContent = task.done ? Notice the architecture: tasks is the single source of truth, render() is the only code that touches the DOM list, and every change (add, toggle, delete) updates the array, saves, then re-renders. The filter() call for deletion keeps every task except the clicked index — a pattern worth memorizing.

Two capstone-level mistakes to watch for. First, forgetting to call saveTasks after a change: toggling works on screen but reloads lose it — the rule is that every function mutating tasks saves before returning. Second, stale indexes: render() rebuilds all buttons fresh each time, so each button's closure captures the correct index. Updating elements in place instead would let indexes drift and toggle the wrong task — which is why the rebuild pattern is recommended.

Natural extensions, each an evening's work: an All / Active / Completed filter, an edit button, a remaining-tasks counter, or due dates. Each reuses the same architecture — update the array, save, re-render — which is the real lesson: apps grow by adding small pieces, not by rewriting.
