This lesson introduces SQL, the standard language for asking questions of databases. By the end you will write queries that select columns, filter rows, sort results, group data, and compute counts and averages — the core of real database analysis. Spreadsheets are wonderful up to tens of thousands of rows; databases hold millions, and SQL is how analysts reach into them. The good news: basic SQL reads almost like English, and everything in this lesson works in any standard database.

Picture a database table as a spreadsheet that lives on a server: named columns, one row per record. Our running example is an orders table with columns order_id, order_date, product, quantity, price, and region. The simplest query asks for columns:

SELECT product, quantity, price FROM orders;

This returns every row but only those three columns. SELECT * returns all columns — fine for exploring, but name your columns in real work so results are predictable. Add a filter with WHERE, which keeps only rows matching a condition:

SELECT product, quantity FROM orders WHERE region = 'North';

Text values go in single quotes; numbers do not: WHERE quantity > 10. Combine conditions with AND, OR, and NOT: WHERE region = 'North' AND quantity > 10. Sort with ORDER BY: ORDER BY order_date gives oldest first, ORDER BY price DESC gives most expensive first (DESC means descending; ASC is the default). Limit huge results with LIMIT 20 while exploring, so a mistaken query returns twenty rows instead of twenty million. Read a query top to bottom as a sentence: "select these columns from this table where these rows, ordered this way." That reading habit makes SQL far less intimidating.

Aggregation is where SQL earns its keep: GROUP BY collapses rows into groups and computes one summary row per group. Total revenue per product:

SELECT product, SUM(quantity * price) AS revenue
FROM orders
GROUP BY product
ORDER BY revenue DESC;

SUM, COUNT, and AVG do the adding, counting, and averaging; AS names the result column so it reads clearly. COUNT(*) counts rows; COUNT(price) counts non-empty prices. Filter groups with HAVING, which is WHERE's counterpart after grouping: HAVING SUM(quantity * price) > 1000 keeps only products above that revenue. A common beginner confusion is WHERE versus HAVING: WHERE filters individual rows before grouping ("only northern orders"), HAVING filters the grouped results after ("only products totaling over 1000"). You will often use both in one query. Date filtering uses the same comparisons: WHERE order_date >= '2026-10-01' AND order_date < '2026-11-01' grabs October cleanly — note the pattern of "from the first of the month up to but not including the first of next month," which avoids missing the last day's late orders.

Two more essentials round out the basics. DISTINCT removes duplicates: SELECT DISTINCT region FROM orders lists each region once — the quickest way to see what values a column actually contains, which doubles as a data-quality check (expecting three regions and finding five spellings is a Lesson 3 problem surfacing in SQL). And NULL marks missing values: a blank in a database is NULL, and it needs special tests — WHERE price IS NULL finds the missing ones, because = NULL never matches anything (a classic gotcha: the query runs fine and returns nothing, silently). Treat NULL with the same care Lesson 3 taught for blanks: understand why it is missing before deciding what to do with it.

Two mistakes dominate early SQL. First, forgetting that SQL is case-insensitive for keywords but your data may not be: 'North' and 'north' can be different values in the region column, so a filter that returns nothing might be a capitalization mismatch — check with SELECT DISTINCT first. Second, grouping errors: every column in your SELECT must either be in the GROUP BY or wrapped in an aggregation like SUM. SELECT product, region, SUM(quantity) ... GROUP BY product is an error (or worse, silently wrong in lenient databases) because region is neither grouped nor aggregated. The rule is mechanical: if it is not aggregated, it must be in the GROUP BY.

Practice: On paper or in any free SQL practice tool, imagine the orders table with ten rows you invent (mix products, regions, quantities, and include one NULL price and one duplicate-looking row). Write and "run" in your head: (1) all orders from the North region sorted by price, highest first; (2) total revenue per product, highest first; (3) the count of orders per region; (4) products with total revenue above 500. For each query, write one sentence saying what business question it answers. Then write the query that finds rows with missing prices, and explain why = NULL would fail where IS NULL succeeds.
